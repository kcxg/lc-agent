# 用户角色管理 任务计划

> 目标：让管理员能给用户分配角色（管理员 / 普通用户），并保护系统账号不被误改。
>
> 整理日期：2026-09-08（grill 讨论后定稿）
> 状态：**已实现**（2026-09-08）。后端 + 前端均已落地，全量测试 388 passed
> 实施顺序：**先做本功能，再做 `lcagent_as_mcp`**（2026-09-08 定）

---

## 0. 先纠正一个前提：角色不是"没有"，是"不能分配"

现状（代码级核实）：

| 层 | 现状 |
| --- | --- |
| 数据 | `models_auth.py:17` `role: str = "user"`（admin / user），**字段已存在** |
| 后端判定 | `auth_middleware.py:60` `require_admin` 守着所有管理接口；<br>`agents.py:211`、`automation.py:282` 按 role 决定 agent 可见性 —— **一直在用** |
| 创建用户 | `admin.py:55` **硬编码 `role="user"`**，管理员建出来的一律是普通用户 |
| 改角色 | **没有任何接口** |
| 前端 | `AdminView.vue:16-19` 有"角色"列，但只是 `el-tag` 展示，**改不了** |

所以本任务要补的只有两件事：**创建时可选角色** + **事后可改角色**，外加系统账号保护。

---

## 1. 目标与非目标

### 目标
1. 管理员创建用户时可选角色（默认 `user`）
2. 管理员能修改已有用户的角色
3. 系统账号（`lcagent_as_mcp_user`）在界面上被标记、角色锁定、不可删除
4. 不允许把系统里最后一个管理员降级或删除（否则锁死后台）

### 非目标
- **不引入第三种角色**。本期只有 admin / user 两种
- 不做"自定义角色 + 权限组"（那是另一个量级的功能，等真有需求再说）
- 不改 `role` 的判定逻辑（`require_admin`、agent 可见性都保持不变，只是现在能配了）

---

## 2. 设计决策

### 2.1 角色集合：保持 admin / user 两种

`User.role` 是字符串字段，但**不做枚举化改造**——改动面大且收益低，约定只写这两个值即可。

不引入 `mcp` 之类的专用角色：服务用户靠 `username` 就能识别，不需要新角色语义。

### 2.2 系统账号保护（本任务的重点）

`lcagent_as_mcp` 会自动创建 `lcagent_as_mcp_user`（见 `docs/tasks/lcagent_as_mcp.md` §3.5）。
它会显示在用户列表里，管理员可能手滑把它改成 admin——**而 MCP 端点是不鉴权的，
这一改等于把管理员权限开放给任何能访问 8001 的人。**

因此：

| 规则 | 说明 |
| --- | --- |
| 标记 | 用户列表里系统账号显示"系统"标签，与普通用户区分 |
| 角色锁定 | 系统账号的角色下拉**禁用**，恒为 `user` |
| 不可删除 | 删除按钮禁用 |
| 不可改密码 | 它是程序用账号，改密码没有意义 |

判定方式：按 username 匹配配置里的 `service_username`（默认 `lcagent_as_mcp_user`），
**不新增表字段**——避免为一个人加一列。

### 2.3 最后一名管理员保护

降级或删除前校验：如果目标用户是 `admin`，且系统中 `role == "admin"` 的用户只剩它一个，
**拒绝操作并返回明确错误**，而不是静默执行。

符合项目一贯的 fail-fast 取向：不做"降级后自动把别人提为 admin"这种自作聪明的兜底。

### 2.4 管理员不能改自己的角色（已定，2026-09-08）

**禁止管理员给自己降级或升级。**

理由：降级后立刻失去管理权限。§2.3 的"最后一名 admin"保护只挡得住"系统里只剩这一个 admin"
的极端情况，挡不住更常见的——把自己降了，剩下的管理员不知情、或根本没人有权限再把他提回来。

实现：改角色接口校验 `target_user_id == current_user.id` → 直接拒绝，
返回明确提示"不能修改自己的角色"。不做静默忽略。

### 3.3 数据

**不新增表、不加字段。** 系统账号靠 username 匹配识别。

### ⚠️ 一个实现中的发现：最后一名 admin 保护是死代码

`_assert_not_last_admin()` 在当前规则下**永远触发不到**：

- 系统只剩 1 个 admin 时，那个 admin 必然是当前登录者本人
- 而"不能改自己角色""不能删除自己"两条规则会**先**把它拦掉
- 所以 `count(admin) <= 1 and user.role == 'admin'` 这个分支进不去

**仍然保留它**，作为防御性兜底——万一将来放宽"不能改自己"，没有它就会把最后一名管理员降级，
后台直接锁死。成本一行判断，收益是避免一个很难排查的坑。

## 6. 已定的决策

1. **系统账号显示在用户列表** — 显示，但标记"系统"、角色下拉禁用、删除禁用
2. **管理员不能改自己的角色** — 见 §2.4
3. **不做"最后一名管理员"之外的额外保护**（如禁止删除 30 天内创建的 admin）— 过度设计
