# lcagent_as_mcp 双工具模式改造计划

> 目标：把"每个 agent 一个 MCP 工具"改成固定 2 个工具（目录 + 调用），
> 工具数恒定不随 agent 数增长，且支持不重连发现新增 agent。
>
> 整理日期：2026-09-09（讨论后定稿）
> 状态：**已实现**（2026-09-09）。实现在 `lc_agent/lcagent_as_mcp/`
> 的 `tool_builder.py` / `server.py`，测试 `tests/test_lcagent_as_mcp.py`。
> 变更点：原设计的重名消歧（`名字(id前8位)`）取消——agent 名就是英文，
> 且由数据库唯一约束 `uq_agent_presets_name` 保证不重名，目录键即 `name`。
> 迁移：`20260909_unique_preset_name`；若已有重名数据，迁移会 fail-fast，
> 须先修正数据，绝不静默改名。
> 快照生成时机定为"每次 `tools/list` 实时查库"，与目录工具同一数据源。
> 前置背景：`docs/tasks/lcagent_as_mcp.md`（v1：N 工具模式，已被本文取代）

---

## 1. 为什么要改（当前 N 工具模式的三个问题）

1. **工具数随 agent 数线性增长**。挂 30 个 agent 就是 30 个工具，
   模型选择准确率随工具数下降，主 agent 的提示词和 schema 占用也线性膨胀
   ——这正是当初做 lcasmcp 想解决的"nbrag 13 个方法太多"问题，在上一层复发。
2. **客户端工具列表是连接时快照**。新增 agent 后客户端必须重连才能发现，
   而重连的时机由客户端决定，server 无法主动推送。
3. **agent 发现信息分散**。"有哪些 agent 可用"这件事没有统一的、
   可随时查询的入口，外部 agent 只能依赖连接时拿到的快照。

## 2. 设计（2 个固定工具）

### 工具 1：`list_lca_agents`（动态目录）

- **职责**：实时查库，返回当前所有可暴露的 mcpagent 名字 + 委派描述
  （建议同时带上每个 agent 的调用示例，即 prompt 该怎么写）
- **入参**：无
- **关键语义**：调用时实时查，不做缓存 —— server 侧加 agent 即时可见，
  外部 agent 的 MCP **不用重连**就能知道新增了哪些 mcpagent
- **每次调用的成本**：一次库查询，很便宜

### 工具 2：`invoke_lca_agent`（调用分发）

- **职责**：按名字调用指定 agent
- **入参**：
  - `agent_name`：字符串，目标 agent 的名字（**不再是一组枚举工具名**，
    从"客户端可见的枚举"变成了"运行时校验的字符串"，拼错要到调用时才发现）
  - `prompt`：发给该 agent 的任务描述
- **工具描述**：两部分
  1. **agent 列表快照**（连接时生成的名字 + 委派描述）—— 常用路径不用多调一次工具 1
  2. **prompt 写作指南** —— 大幅参考子 agent task 工具的描述
     （任务自包含、写清背景和目标、说明期望输出格式、子 agent 看不到主对话上下文），
     因为本质是同一个东西：把任务委派给一个没有主对话上下文的子 agent

### 两层快慢路径

| 路径 | 什么时候用              | 数据来源         |
| ---- | ------------------- | ------------ |
| 快路径 | 照着工具 2 描述里的快照直接调 | 连接时生成的 agent 列表 |
| 慢路径 | 快照 miss 时先调工具 1   | 实时查库          |

弱模型走快路径也能成功；强模型遇到列表里没有的目标会主动调工具 1。

## 3. 已识别的坑与对策

1. **快照过期**：外部 agent 照快照调一个刚加的新 agent 会 miss。
   对策：
   - 工具 2 描述里写明"列表非最新，找不到目标时先调 `list_lca_agents`"
   - **调用一个不存在的名字时，错误信息里把最新列表带回来**
     —— 一次失败调用顺便完成发现，模型可立即纠错重试，不用再调工具 1
2. **名字拼错**：错误返回里带合法名字列表，让模型自己对照纠错（同上）。
   如果在错误信息里做模糊匹配（"你是不是想调 X？"）可以再降一档重试成本，
   但属于加分项，非必需。

## 4. 不改的部分

- 模块结构、挂载方式、服务用户、危险工具组过滤、鉴权策略
  —— 这些 v1 都已实现且与工具暴露形态无关，原样保留
- 复用 `tool_builder.py` 的暴露过滤逻辑（`can_be_subagent` 且不含
  `file_write`/`command`），只是输出从"N 个工具"变成"1 份目录数据"
- 复用 `runner.py` 执行链路，`invoke_lca_agent` 内部按 `agent_name`
  查库定位后走原执行链路

## 5. 实现步骤（按此顺序，每步可独立验证）

| 步 | 内容                                       | 验证方式                                  |
| - | ---------------------------------------- | ------------------------------------- |
| 1 | `server.py` 的 `list_tools` 固定返回 2 个工具          | 客户端连接后只看到 2 个工具，不管库里有多少 agent       |
| 2 | 实现工具 1：实时查库返回 agent 目录                 | 新增一个 agent（不重连）后调工具 1 能看到它          |
| 3 | 实现工具 2：按名字调用，prompt 走原执行链路             | 快照内的 agent 调用成功，用量正常记账              |
| 4 | 工具 2 描述嵌入连接时快照                          | 客户端在工具描述里直接看到 agent 列表               |
| 5 | 错误信息携带最新列表                              | 调一个不存在的名字，返回的报错里带完整 agent 目录，模型据此重试成功 |

## 6. 待确认

1. **快照的生成时机**：推荐在 `initialize` 时生成并嵌进工具 2 的描述
   （`list_tools` 被调用时重新查一次库也可以，语义差异不大，实现取更简单者）
2. **调用示例放哪**：推荐工具 1 返回里带每个 agent 的 prompt 示例，
   工具 2 描述快照里只留名字 + 委派描述
3. **错误信息里带最新列表的触发条件**：推荐只要 `agent_name` 不在库里就触发
   （无论是不是快照过期导致），统一走"报错 + 目录"一个出口
